# 2026-03-27 阶段总结：GISEC 现在走到哪一步了

## 先说结论

这个项目现在已经把主线重新理顺了。我们前面花了不少时间试过 `U-Net + split-first + reference + graph` 这条路，结果证明它更像一个研究想法，不像一个能直接拿来冲指标的正式主线。现在更对的方向已经很清楚了：先用强实例分割主干把“一个零件就是一个实例”这件事做对，再把 `reference` 和 `graph` 放回去做它们真正擅长的事。

现在最好的新主线短矩阵结果是 `Mask2Former@1024`，`segm/AP = 25.34`。这个结果比之前的 U-Net 基模强很多，但离我们的目标还差得很远。这个结果说明方向对了，但工作还远没有完成。

## 这个项目到底在做什么

这个项目要解决的是电子元件堆叠场景里的实例分割问题。简单说，画面里会有很多电子元件堆在一起，系统要把每一个零件单独分出来，而且边缘还要足够准，因为后面还要做抓取、定位和姿态相关的工作。

这个任务看起来像普通分割，但其实难得多。普通前景分割只要把“哪里有东西”分出来就行。这个任务不一样。这个任务要回答的是：

- 这一片到底是一个零件，还是两个贴在一起的零件
- 细引脚、孔洞、缺口、反光和阴影会不会把一个零件弄得断断续续
- RGB 看起来连在一起的地方，深度是不是其实已经断开了

所以这个任务的重点不是“有没有前景”，而是“实例粒度对不对，边缘够不够准”。

## 这个场景为什么难

### 1. 零件很小，而且长得很密

很多电子元件本身就很小，堆叠之后又贴得很近。模型很容易把几个零件看成一整块，也很容易把细小部分漏掉。

### 2. 形状不规则，细节很多

这个场景里有很多细引脚、长条、孔洞、非凸形状。对这种目标来说，框级方法有时会把背景带进来，普通语义分割方法又容易把实例连成一片。

### 3. RGB 和深度各有用，但也各有问题

RGB 对纹理、颜色和边缘更敏感。深度对分开接触目标、判断层次关系更有用。但深度不是万能的。深度进得不对，也会把实例关系带偏。我们前面的实验已经看到，深度如果过早地主导 split，有时反而会让多个零件更容易粘在一起。

## 我们前面是怎么想的

项目最早的核心想法是，先用一个轻量模型把图像切成很多片，再用 `reference` 和 `graph` 去判断哪些片属于同一个零件，最后再把它们合起来。

这个想法本身不是错的。它有两个很有价值的点：

- `reference` 能提供“一个真实零件大概长什么样”的先验
- `graph` 能处理“这些局部区域之间是什么关系”

但前面的问题也很明显。第一阶段如果本身就没有把实例粒度做对，后面的 `reference` 和 `graph` 就会变得很被动。它们本来应该做“关系判断”和“局部修正”，结果却被迫去救一个很弱的主干。这会让系统越来越复杂，而且很难稳定。

所以现在我们的理解已经变了。

现在更清楚的设计思路是：

- 第一步先用强实例分割主干，把实例粒度做对
- 第二步再把边缘质量提上去
- 第三步再把 `reference` 和 `graph` 接回去，做更难的关联和关系建模

这也更符合这个项目最后想做成的样子。最后的 GISEC 仍然要有 `reference` 和 `graph`，但它们不能再建立在一个明显偏弱的第一阶段上。

## 到现在为止，我们实际做了什么

### 1. 我们把旧主线真正试明白了

我们前面认真跑过 `U-Net split-first` 这条线。结论已经很明确了：`U-Net` 很擅长前景和边缘，但它不适合直接当这个任务的正式第一阶段实例分割主干。

前面这条线里最好的结果是：

- `unet_rgb_full_calibrated_eval`
- `segm/AP = 4.12`
- `bbox/AP = 3.57`

这个结果的意思很直接。它说明 U-Net 这条线可以学到一些局部结构，也可以把大块连成一片的问题压下去一部分，但它离“正式可用的实例分割主干”还差得很远。

### 2. 我们把基模竞赛主线搭起来了

这一步其实很重要。因为前面的代码库里同时有很多研究线，入口不统一，脚本很多，配置也比较散。这样很难做公平比较，也很难知道问题到底出在哪一层。

现在我们已经把这一层整理成了更清楚的正式主线：

- baseline 主线统一走一个 runner
- `Mask R-CNN` 和 `Mask2Former` 都有正式的 Phase A 入口
- 训练过程统一产出 `best/final` checkpoint
- 训练过程统一产出曲线图和可视化
- summary 字段统一，后面可以直接横向比较

这一步不直接提升 AP，但它把后面的试验顺序理顺了。

### 3. 我们跑完了第一轮 RGB 短矩阵

这一轮我们只做了最基础、也是最关键的事：先看强实例主干本身能不能把实例粒度做对。

我们比较了两类 backbone：

- `Mask R-CNN`
- `Mask2Former`

我们也比较了三个分辨率：

- `256`
- `512`
- `1024`

结果非常清楚。

只有 `1024` 跑出了非零而且有意义的结果。`256` 和 `512` 在这轮短程协议下全部是 `0 AP`。这基本说明在这个任务上，分辨率不是一个小调节项，而是很关键的条件。

## 当前最重要的实验结果

### 最好的短矩阵结果

现在最好的短矩阵结果是：

- `mask2former_swin_t_1024_phasea_short`
- `segm/AP = 25.34`
- `segm/AP50 = 51.91`
- `segm/AP75 = 23.66`
- `bbox/AP = 30.46`
- `F1@50 = 60.16`
- `boundary IoU = 11.62`

这个结果有两个意思。

第一，这个方向比前面的 U-Net 主线明显更靠谱。  
第二，这个结果离目标还很远，还不能说明我们已经找到最终解。

### 第二名结果

第二名是：

- `mask_rcnn_r50_1024_phasea_short`
- `segm/AP = 5.11`
- `bbox/AP = 11.85`
- `F1@50 = 32.26`

这个结果说明 `Mask R-CNN` 也比旧 U-Net 主线更像一个正式实例分割 backbone，但它目前明显落后于 `Mask2Former@1024`。

### 这轮结果最有价值的地方

这轮最有价值的结论不是“某个模型高了多少”，而是下面这三点：

- `1024` 是当前任务里的必要分辨率，不是可有可无的选项
- `Mask2Former` 现在是最值得继续推进的正式主线候选
- `U-Net` 更适合作为后面的边界 refinement 思路来源，不适合继续直接扛第一阶段主干

## 项目现在进行到哪了

现在项目已经从“多条研究线一起试”的状态，转成了“正式主线先做强 backbone 竞赛”的状态。

现在的阶段可以简单理解成这样：

- 旧的 `query/GISEC alpha` 线先暂停
- 旧的 `split-first U-Net` 线保留作对照和病灶分析
- 正式主线先跑强实例 backbone
- `reference` 和 `graph` 先不抢主预算

从实验节奏上看，现在已经完成了：

- U-Net 主线的阶段性验证
- baseline 主线入口的统一
- RGB short-matrix 的首轮比较

现在已经开始了：

- `mask_rcnn_r50_1024_phasea_full`
- `mask2former_swin_t_1024_phasea_full`

也就是说，短矩阵已经给出方向了，full-run 现在正在接着跑。

## 现在最核心的问题是什么

### 1. 我们离目标还有明显距离

现在最好的新主线短矩阵结果是 `25.34 AP`。这个结果比前面强很多，但离“明显超过传统 RGB/RGB-D 模型”和“断层领先”的目标还差很远。

### 2. 这个任务对分辨率非常敏感

这一点现在已经很清楚了。`256/512` 没站住，`1024` 才开始有像样的结果。这意味着后面所有 serious run 都要围绕 `1024` 设计。这样会带来更高的显存和时间压力。

### 3. RGB-D 还没有被认真放回正式主线

我们前面做过一些深度相关尝试，但还没有在“已经证明有效的强 backbone”上严肃比较 `rgb / rgbd_concat / rgbd_calibrated`。所以现在还不能下结论说深度到底在哪一层最有用。

### 4. `reference` 和 `graph` 还没有在强 backbone 上证明价值

这两个模块仍然是项目最后必须保留的核心部分。但现在它们还没有建立在一个已经过线的 backbone 上。所以它们的价值还不能用正式结果来证明。

## 现在对这个项目的理解，已经和一开始不一样了

一开始我们更像是在问：“怎么把 `reference` 和 `graph` 做得更强？”  
现在我们更像是在问：“在这个场景里，一个真正靠谱的基础实例分割主干到底是什么？”

这个变化很重要。因为它让整个项目的顺序变对了。

现在更合理的顺序是：

1. 先找到强 backbone
2. 再把 RGB-D 放到这个 backbone 上认真比较
3. 再做边界 refinement
4. 最后再把 `reference` 和 `graph` 放回正式主线

这个顺序的好处是简单，也更容易解释。每一步都能单独回答一个问题，不会把很多变量混在一起。

## 下一步怎么想

现在最推荐的主线没有悬念，就是：

- 先把 `Mask2Former@1024` 和 `Mask R-CNN@1024` 的 full-run 跑完
- 然后冻结 winner backbone
- 然后只在 winner 上做 RGB-D
- 然后只在 winner 上做边界 refinement
- 最后再把 `reference` 和 `graph` 接回来

现在不该做的事也很清楚：

- 不该再回到 U-Net 直接做正式第一阶段主干
- 不该同时改 backbone、分辨率、RGB-D 融合和 reference/graph
- 不该在 backbone 还没过线的时候，让后面的模块承担主结果压力

## 一句话收尾

这个项目现在最大的变化，不是某个数字涨了多少，而是主线终于变清楚了。我们现在已经知道旧的第一阶段为什么不行，也已经看到强实例主干在这个场景里确实更像正确方向。接下来真正决定项目上限的，就是这轮 `1024 full-run` 的结果，以及 winner backbone 上的 RGB-D 和 `reference + graph` 能不能继续把上限抬起来。
